# FinoraOS decisions

## Stack and boundaries

- **All-TypeScript pnpm monorepo:** shared platform contracts remove enum drift between Next, Nest and agents. Node 24 LTS is pinned; Node 26 is accepted for this development environment.
- **Next 16 + React 19 + Nest 11:** current compatible versions were checked. FinoraOS uses its own component system in `packages/ui`, with locally bundled Manrope typography and shared Finora tokens/primitives. Razorpay Blade is intentionally not a runtime UI dependency; we retain Finora’s own product identity and visual conventions.
- **Prisma 7 + PostgreSQL:** Prisma 7 uses `prisma.config.ts` for the migration connection URL and `@prisma/adapter-pg` in the runtime client. This matches current tooling and prevents schema-editor version drift. Persistence stays behind domain services/repositories when queries become non-trivial.
- **Agent database identity:** development bootstraps a dedicated `finora_agent_ro` PostgreSQL role. It has schema/table `SELECT` only, no sequence privileges, no inherited privileges or `BYPASSRLS`, and `default_transaction_read_only` enabled. Its row-level-security policies require a transaction-local organization context; without one, or with an unknown organization, it returns no rows. The API's controlled read tools use this role rather than the application/migration identity. The model still never receives SQL or a database credential—it can select only a Zod-validated tool from the explicit catalogue.
- **Governed agent writes:** `finora_agent_rw` is a separate `NOBYPASSRLS` PostgreSQL identity with tenant-scoped reads and column-level `UPDATE` grants on six editable finance record types. It cannot change identifiers or organization ownership and has no `DELETE`, `TRUNCATE`, arbitrary `INSERT`, schema, or sequence privileges. Chat write mode lets the controller create only a typed, expiring before/after proposal. An authorized user must approve that exact diff; the executor then atomically claims the pending proposal, checks the record version, writes the allowlisted fields, and appends the audit event. The model receives neither SQL nor the writer credential and never executes the proposal itself.
- **Gateway boundary:** vendor SDKs live under `apps/api/src/gateways`; business modules depend on contracts, not Razorpay/Ollama implementations.
- **Pure reconciliation package:** `@finora/reconciliation` owns the deterministic matching pipeline and has no Nest, Prisma, HTTP, AI, environment, clock, or mutable-state dependency. The API maps organization-scoped imported records into explicit engine inputs, then persists its output transactionally. Evaluation and API orchestration use this exact engine, preventing metric/demo drift.
- **Persisted UI-message chat:** Vercel AI SDK `useChat` consumes a same-origin UI-message stream containing typed artifacts/tool activity. Nest persists organization/user-scoped threads, messages, and controller AgentRuns. Answers are currently computed before streaming; token-level provider streaming remains later work.
- **Controlled chat actions:** a recognized exception reference such as `Investigate EXC_005.` routes to `AgentsService`, not a generic LLM prompt. The investigator is organization-scoped and persists its AgentRun, typed proposal, exception operational state, and audit event atomically. This does not mutate raw finance records and never approves or closes an exception; approval and closure remain separate explicit operations.
- **Multi-step controlled finance agent:** `FinanceAgent` selects one or more allowlisted, Zod-validated tools over bounded conversation context. Safe representation differences are normalized before deterministic, organization-scoped execution. The model receives neither SQL nor credentials, numeric synthesis is evidence-checked, and record lists use deterministic summaries/tables.
- **Chat context and exact references:** the current message outranks chat history. Explicit finance topics and record IDs discard stale context, while short pronoun follow-ups receive only bounded recent context. Exact payment/settlement/exception references, latest-payment requests and workspace capability checks use deterministic fast lanes through the same tenant-scoped tools; the LLM remains responsible for ambiguous planning rather than verified identifier resolution.
- **Cash movements and adjustments:** cash position/forecast use a currency-bearing account plus immutable posted/scheduled movements. Approved typed proposals create idempotent derived adjustments and audit events, never changes to imported source rows, before reconciliation reruns.
- **Keycloak identity, database-owned authorization:** Keycloak supplies authenticated identity, realm roles, and the organization claim. Nest verifies issuer and audience, then resolves `sub + organization_id` to an active database membership. The database role is authoritative for application permissions, so changing a token alone cannot grant access. Local Keycloak runs in development mode and is not a production deployment recipe.
- **OIDC redirect with a Finora-owned theme:** FinoraOS does not collect enterprise passwords in the Next.js application or enable the OAuth password grant. Authentication remains on Keycloak's authorization endpoint, themed with versioned Finora assets so the user experience is consistent. This retains the authorization-code/PKCE security boundary and keeps future SSO, MFA, and federation possible.
- **Coordinated logout and explicit lifetimes:** logout clears the encrypted NextAuth JWT cookie, then calls Keycloak's RP-initiated logout endpoint with `id_token_hint`, `client_id`, and an allowlisted post-logout redirect. Subsequent authorization uses `prompt=login` to prevent silent demo-account reuse. Access tokens last 5 minutes, inactivity is capped at 30 minutes, and both Keycloak and NextAuth enforce an 8-hour absolute maximum.
- **Generic organization nodes:** offices, departments, teams, cost centres, and employee positions share one parent/child `OrganizationNode` tree. Budgets attach to nodes and explicit periods instead of requiring a table per hierarchy level. This keeps rollups extensible without pretending V1 implements a full general ledger or workforce system.
- **Budgets and spend limits are distinct:** budgets remain planning allocations. `@finora/spend-policy` deterministically enforces period/currency hard limits across node subtrees and ancestors. Category limits are soft: the financial record is retained, while deduplicated warnings go to finance controllers/admins and the node owner. Child limits and direct-child allocations cannot exceed the parent envelope.
- **Audited finance imports:** CSV uploads live in Records and create organization-scoped `ImportBatch` records. Payable invoices and employee expenses are validated row by row, checked against the same spend engine, partially accepted only with an honest error report, and audited. Receivable invoices do not consume spend limits.
- **Manual finance records and corrections:** Records supports single-record creation and optimistic-concurrency edits in addition to CSV ingestion. Imported source metadata remains intact; every correction records full before/after evidence in the shared tenant audit trail. Chat-originated corrections require the stricter proposal/approval flow above.
- **Expense category provenance:** explicit user/import categories are confirmed; deterministic merchant rules run before the AI categorizer; AI output is schema-validated and remains a suggestion or review item. Category selection never changes the source amount.
- **Receipts are evidence, not transaction mutations:** expense claims, immutable document metadata, and receipt requests are separate records. Uploading a receipt stores bounded content through a document-storage gateway, records its hash/source, links the evidence, and audits the state transition; it does not rewrite an imported transaction.
- **Custom skills are bounded procedures:** a skill is organization-owned prompt guidance plus an allowlist of existing read tools. The controller may select an active skill, but the skill cannot add permissions, SQL, credentials, or write capabilities. Runs retain the selected skill/version context for audit.
- **Simple scheduled jobs before a queue:** Nest scheduling is sufficient for V1 receipt reminders and deterministic manual runs. Job/run rows provide operational visibility. Durable distributed execution, leases, retries, backoff, and dead-letter handling are required before using this design for production connector ingestion.
- **Connector control plane and secret references:** `IntegrationConnection` stores provider, state, metadata, and a credential reference—not raw secrets. Provider code remains behind gateway contracts. The Razorpay adapter accepts test keys only and normalizes API amounts from minor to major currency units; synchronization, cursors, and webhooks are intentionally separate orchestration work.
- **Local document storage is a development adapter:** local files under `.data/documents` make the receipt workflow testable without paid infrastructure. Production must replace it with private object storage, malware scanning, encryption/retention controls, and an authorized download path.

## Financial and AI safety

- **Money:** PostgreSQL `Decimal(18,2)`, decimal strings at API boundaries, and `decimal.js` for TypeScript arithmetic. Never use float addition for financial decisions.
- **Deterministic first:** IDs, references, amounts, date windows and settlement math are deterministic. The reconciliation stages are exact reference → settlement relationship → date window → explicit composite score. A candidate is consumed only once; ties, mismatches, low-confidence candidates, and missing counterparts become exceptions. AI sees only those exceptions and produces typed proposals validated by Zod. It cannot run arbitrary SQL or mutate records.
- **AI gateway selection and fallback:** `AI_PROVIDER=auto` selects the first configured hosted API key in documented order (Gemini → Groq → OpenRouter), otherwise native Ollama. A hosted completion failure retries through Ollama. `AI_PROVIDER=mock` is explicit and reserved for deterministic tests/CI. The exception investigator and settlement chat both use the same API-owned gateway via a controlled adapter; agents never access vendor SDKs or Prisma.
- **Structured operational logs:** the API uses a small Pino wrapper with request IDs, configured `LOG_LEVEL`, and credential redaction. Development output is compact and human-readable; production output is structured JSON. We log lifecycle events, request completion, gateway choice/completion/fallback, reconciliation metrics, and agent-run lifecycle without logging prompts, financial record bodies, secrets, or authorization headers.
- **Local AI:** Native Ollama is preferred over Docker for the target GPU. Settlement amounts and conclusions are always computed with `decimal.js`; local-model output is accepted only as a constrained, schema-like qualitative explanation with no amounts or calculations.
- **Approvals/audit:** proposed adjustments are internal simulations in V1 and require approval before a status is closed. Raw source metadata remains traceable.

## Current production boundaries

No production claims or real-money actions are made. Authentication and role checks are implemented, but the bundled Keycloak server is development-only. Razorpay supports sandbox reads but not synchronization/webhooks; Slack supports outbound reminders but not inbound receipt events. Banking/ERP connections, OCR, complete GST/TDS compliance, durable job execution, autonomous policy closure, and full dark theme remain roadmap work.
